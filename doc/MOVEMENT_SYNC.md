# 이동 격차 진단과 재동기화

웹 클라이언트는 200ms마다 실제 예측 위치·회전·층을 `PlayerMovementSample`로 보낸다. `PlayerMove.position`은 클릭 이동의 목적지일 수 있으므로 격차 측정에 쓰지 않는다. 샘플은 진단용이며 서버 좌표를 변경하지 않는다. X축 격차는 월드 경계 순환을 반영한다.

서버는 최근 30초의 샘플을 메모리에 보관한다. 각 샘플에는 클라이언트 자세, 서버 자세, 큐 길이, 가장 오래된 요청의 대기 시간, 최근 서버 이동 tick이 들어간다. 서버에서도 최소 150ms 간격과 최대 201개 제한을 적용한다. 기존 요청·tick 상세 이력은 각각 최근 16개를 유지한다.

수평 격차가 `max(3m, 최근 서버 이동 속도 × 0.5초)` 이상으로 600ms 지속되면 `divergence_started`를 기록한다. 임계값 절반 미만이면 `recovered`를 기록한다. 1초 넘게 샘플이 끊기면 지속 시간 판정을 다시 시작한다. 시작 이력 출력에는 플레이어당 30초 제한을 둔다.

일반 플레이어의 큐가 24개인 상태에서 추가 경유점이 들어오면, 상한 32개에 도달하기 전에 다음을 수행한다.

1. `queue_resync`에 서버 자세, 거절한 이동 요청, 큐 길이와 직전 이력을 기록한다.
2. 서버 이동 큐를 비우고 서버 좌표·회전·층 및 `resync_id`를 `MovementResync`로 보낸다.
3. 일치하는 `MovementResyncAck`가 도착할 때까지 이동·회전·탑승 복구·층 변경·위치 샘플을 버린다. WebSocket의 메시지 순서로 보정 이전 요청과 이후 요청을 구분한다.
4. `resync_acknowledged`에 수신 확인까지 걸린 시간과 버린 메시지 수를 기록한다.

웹은 예측 상태를 초기화한 뒤 확인 메시지를 보내고, 클릭 목적지와 자동 여행 목적지에서 경로를 다시 계획한다. 누르고 있는 이동 키는 다음 프레임부터 처리한다. CLI도 다음 명령보다 먼저 확인 메시지를 전송한다. 보정 간격은 최소 2초이며, 그동안 큐가 다시 24개에 닿으면 추가 경유점을 받지 않는다. 공식 NPC의 기존 경로 처리는 유지한다.

로그는 `movement_audit` 대상의 `Movement sync trace` 헤더와 `Movement sync history` 이력으로 나눈다. 동일한 `trace_id`로 묶고, 이력은 `kind`별 `part`(0부터 시작), `parts`, `entries`를 합친다. 종류는 `samples`, `requests`, `ticks`, `recovery_events`, `counters`다. 긴 journal 메시지를 읽을 때는 `journalctl --all -o json`을 사용한다.

프로토콜 버전은 90이다. 서버·웹 WASM·CLI를 함께 갱신해야 한다. 이 보정은 큐 누적을 해소하며, 최초 격차의 원인 규명에는 새로 수집한 이력을 사용한다.
